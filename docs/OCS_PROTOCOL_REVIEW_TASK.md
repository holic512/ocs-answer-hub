# OCS 题库接口适配二次核验与格式修复

> 本文为任务说明，尚未执行接口核验或修复，不是验收报告。

## 一、任务目标

基于当前项目已有代码，对 OCS 网课助手的题库接口适配进行完整的二次核验，并修复已确认存在的请求与响应格式兼容问题。

本次仅处理数据格式、字段类型、字段映射和协议兼容，不进行功能扩展、架构重构或其他无关优化。

| 答案来源 | 当前实现 |
| --- | --- |
| 个人本地题库 | 使用项目现有的数据存储和查询实现 |
| 言溪第三方题库 | 通过已有接口查询答案 |
| OpenAI | 通过现有模型接口生成答案 |

先检查已有实现，保留三种来源当前的查询机制、调用逻辑、优先级、回退规则及相关配置，不重新设计。

## 二、参考资料与核验依据

联网查阅以下资料，并与项目实际代码交叉验证。

### 2.1 OCS 官方开发文档：主要协议依据

https://docs.ocsjs.com/docs/other/api#AnswererWrapper

重点核验：

- `AnswererWrapper` 配置结构。
- 请求方法与请求体生成规则。
- `${title}`、`${options}`、`${type}` 占位符。
- 自定义字段的 `handler` 解析机制。
- 响应 `handler` 的返回格式。
- 多答案、多选题及未命中结果的表示方式。

### 2.2 OCS 官方题库配置教程

https://docs.ocsjs.com/docs/work

结合教程核验项目生成的题库配置是否符合实际使用要求。

### 2.3 言溪题库

https://tk.enncy.cn/

当前对接接口：

```http
POST https://tk.enncy.cn/query
```

当前已获取的请求配置样例：

```json
{
  "token": "<TOKEN>",
  "title": "${title}",
  "options": "${options}",
  "type": "${type}",
  "images": {
    "handler": "return (env) => env.images"
  },
  "v": "2",
  "suggestion_title": "${suggestion_title}",
  "suggestion_options": "${suggestion_options}"
}
```

对应的响应解析器：

```javascript
return (res) =>
  res.code === 0
    ? [
        res.data.answer,
        undefined,
        { tags: res.data.tags }
      ]
    : [
        res.data.question,
        res.data.answer,
        {
          ai: res.data.ai,
          tags: res.data.tags
        }
      ];
```

核验要求：

- 上述内容仅为已获取的第三方配置样例，不代表所有字段及状态码语义均已确认。
- 结合文档、实际代码或可验证的响应样本再次核验，不凭经验推断。
- 如需查阅 OCS 源码，注明源码版本、具体文件及引用位置。
- 区分官方通用协议与特定版本、特定题库的扩展行为。

## 三、核验范围

### 3.1 OCS 请求体解析

| 核验对象 | 核验要求 |
| --- | --- |
| `title` | 字段名称、类型及实际题干内容是否正确 |
| `options` | 字符串、数组及换行分隔字符串是否正确解析 |
| `type` | 单选、多选、判断、填空等题型映射是否正确 |
| `images` | 数组、无图片及字段缺失情况是否正确处理 |
| `suggestion_title` | 是否正确保留和映射 |
| `suggestion_options` | 是否正确保留和映射 |
| `v` | 是否需要接收或向上游传递，以实际协议为准 |
| 空值与缺失值 | 是否兼容空字符串、`null`、`undefined` 和字段缺失 |
| JSON 解析 | 是否存在反序列化或字段类型转换问题 |

所有字段以实际协议和核验版本的实现为准，不得假设 OCS 一定传递全部字段。

### 3.2 三种答案来源的请求映射

#### 个人本地题库

确认 OCS 请求经现有映射后，能够正确传递给本地题库查询逻辑。不修改数据库结构及查询业务逻辑。

#### 言溪第三方题库

确认：

- OCS 请求是否正确转换为言溪所需的数据结构。
- 请求字段名称、类型和序列化方式是否一致。
- 响应解析是否与可确认的实际响应格式一致。
- 状态码、空答案、未命中结果和附加字段是否正确处理。

#### OpenAI

确认：

- 题干、选项、题型和图片等输入是否正确转换为现有接口所需格式。
- 模型响应中的答案提取、JSON 解析和类型转换是否正确。
- 提取结果是否能够进入现有统一答案转换流程。

不得调整模型选择、提示词策略、查询优先级或其他业务行为。只有存在直接导致协议格式错误的代码，并能提供明确证据时，才允许进行对应的最小修改。

### 3.3 查询结果转换为 OCS 格式

检查三种来源的结果能否被当前 OCS `handler` 正确解析，重点核验：

- 题目与答案的字段映射。
- 单选、多选、判断及填空题的答案表示。
- 多选答案的分隔符格式。
- 单条结果与多条结果的表示。
- 未命中、空答案及异常响应的处理。
- `ai`、`tags` 等附加字段的实际支持情况。
- 不同来源结果格式不一致时，现有适配层是否正确转换。

明确区分以下两层：

| 层级 | 核验内容 |
| --- | --- |
| HTTP 响应 | 项目接口实际返回的 JSON 结构 |
| OCS 响应解析 | `handler` 解析 JSON 后返回的数组或 `undefined` |

按照任务提供的官方文档线索，复核 `handler` 对以下结构的支持：

```javascript
[题目, 答案]
```

```javascript
[
  [题目一, 答案一],
  [题目二, 答案二]
]
```

```javascript
undefined
```

其他扩展结构必须通过实际代码或指定版本源码确认，不能直接视为 OCS 通用协议。

### 3.4 闭环验证

分别验证三种来源的完整链路：

```text
OCS 请求
  → 请求解析
  → 来源参数映射
  → 查询响应
  → 结果格式化
  → OCS handler
```

| 场景类别 | 验证内容 |
| --- | --- |
| 常规题型 | 单选、多选、判断、填空 |
| 图片题 | 图片输入、无图片、图片字段缺失 |
| 请求边界 | 缺失字段、空字符串、null 等 |
| 响应边界 | 空答案、未命中、异常响应 |
| 结果数量 | 单条、多条结果，以及当前实现实际支持的形式 |

优先复用现有测试工具和框架，不引入不必要的依赖。

无法真实调用外部服务时，可以使用已有响应样本或模拟数据进行格式验证，但必须明确样本来源与验证范围，不得将模拟测试描述为真实服务调用成功。

## 四、修改约束

1. 只修改与 OCS 请求解析、参数映射、响应格式化直接相关的代码。
2. 不修改本地题库数据库结构及查询业务逻辑。
3. 不改变言溪和 OpenAI 的现有调用策略。
4. 不改变三种来源的查询顺序、回退规则及配置。
5. 不新增无关功能，不重构架构，不扩展其他模块。
6. 优先复用现有 DTO、转换器、适配器和工具方法，避免重复实现。
7. 已正确的实现保持不变，不因代码风格或主观偏好修改。
8. 无法证实的问题列为待确认，不进行猜测性修复。
9. 不输出或记录真实 Token、API Key 等凭据。

## 五、执行流程

### 第一阶段：现状调查

定位 OCS 接口入口、请求解析、题库配置和响应 handler，以及本地题库、言溪、OpenAI 的请求响应适配代码和相关测试，以实际代码说明当前数据流。

### 第二阶段：协议二次核验

对照官方文档、言溪样例和项目代码，逐项核验字段及转换行为。

| 项目 | 内容要求 |
| --- | --- |
| 涉及位置 | 文件路径及具体代码位置 |
| 当前行为 | 现有实现实际如何处理 |
| 协议差异 | 与已确认协议或响应样本的差异 |
| 依据来源 | 官方文档 URL、指定版本源码位置或真实测试结果 |
| 确认状态 | 已证实或待确认 |

不得将推测、未经证实的状态码语义或第三方扩展行为写成确定结论。

### 第三阶段：最小范围修复

只修复已确认的格式映射和兼容性问题，补充直接相关测试，保留原有查询机制、优先级、回退和配置。正确实现保持不变。

### 第四阶段：验证与总结

执行必要测试，输出简洁核验报告：

1. OCS 请求字段核验结果。
2. 本地题库、言溪、OpenAI 三条链路的适配结果。
3. 实际发现及修复的格式问题。
4. 修改文件及对应原因。
5. 实际执行的测试与结果。
6. 尚未确认事项及验证限制。
7. 每项关键协议结论的参考来源。

## 六、最终验收要求

本次任务仅保证 OCS 与现有三种答案来源之间的数据格式正确、字段映射一致、响应解析兼容。

- 已确认问题获得最小范围修复。
- 正确实现和原有业务行为保持不变。
- 关键协议结论具有可追溯依据。
- 实际测试与模拟验证明确区分。
- 未确认问题明确列出，不以猜测性修改代替核验。
- 不因调查发现其他问题而顺带修改无关功能。
