# 运行日志与问题追溯

应用将关键运行事件同时输出到控制台和日志文件，不需要增加配置项。Docker 默认保存到部署目录 `data/ocs-answer-hub/logs/app.log`，本地开发保存到项目根目录 `logs/app.log`。

## 日志文件与保留

- 每行一条 JSON，包含 UTC 时间 `time`、`level`、事件名 `event` 和事件字段。
- 当前日志 `app.log` 达到 10 MiB 后轮转，最多保留 `app.log.1`、`app.log.2`、`app.log.3` 三份历史文件。
- 应用重启继续追加；Docker 挂载后，容器重建和升级保留原文件。
- 开发清理脚本不删除运行日志。需要长期留存的日志应在轮转前自行归档。
- 日志用于运行排错，会按保留策略轮转；数据库中的题库、答案版本和查询记录继续由原业务机制保存。

已有 Docker 部署需为 `init` 和 `app` 增加日志挂载并重新创建容器，操作见[部署说明](../deploy/OPERATIONS.md#已有部署增加日志挂载)。

## 查找一次操作

每个 API 请求由服务端生成独立 `requestId`，通过 `X-Request-ID` 响应头返回。页面请求失败时会显示请求编号，来源测试结果也显示该编号。服务器内部错误的 JSON 响应包含 `requestId`，可提供给维护者查询。

```sh
# 最近的运行记录。
tail -n 100 /data/ocs-answer-hub/logs/app.log

# 实时观察。
tail -f /data/ocs-answer-hub/logs/app.log

# 将下面的编号替换为页面显示的实际值；同时检索当前与历史文件。
grep -F '实际请求编号' /data/ocs-answer-hub/logs/app.log*
```

查题还有独立的 `queryId`，贯穿本地检索、外部来源回退、解析和查询结果。多个相同题目的并发请求可能复用一次执行，各自的 `requestId` 不同，通过同一个 `queryId` 关联。执行阶段使用发起该次执行的请求上下文，每个等待请求仍有自己的完成记录。

文件中的结构示例（编号及题目均为示例）：

```json
{"event":"query.completed","requestId":"示例请求编号","method":"POST","route":"/api/admin/query","actor":"示例管理员","queryId":"示例查询编号","status":"hit","source":"示例来源","answer":"3","durationMs":1200,"time":"2026-10-30T00:00:00.000Z","level":"info","message":"[query.completed]"}
```

## 记录范围

| 范围 | 事件及内容 |
| --- | --- |
| 启动和关闭 | `application.*`：运行版本所在的启动迁移记录、Node 版本、监听地址、配置来源、数据库主机与库名、启动结果、退出信号及关闭失败 |
| 数据库迁移 | `database.*`：检测到的迁移基线、执行的迁移命令阶段、耗时、错误代码和调用位置；不打印连接密码、SQL 原文或子进程原始输出 |
| API 请求 | `http.request.*`：请求编号、方法、路由模板、客户端 IP、已认证管理员、HTTP 状态、耗时；错误记录原因分类和代码位置 |
| 账号与鉴权 | `auth.*`：管理员初始化、登录成功、会话失效、来源或 CSRF 校验失败、必须改密等拒绝原因；失败登录的账号与状态见请求完成记录 |
| 管理操作 | `admin.action`：成功的新增、修改、删除、排序、凭证创建／撤销、密码修改等；包含操作者、资源 ID、脱敏后的输入和允许记录的结果字段 |
| 导入与导出 | 导入记录条数、预览标记和结果，不整批打印导入文件；导出记录条数；单题持久化仍记录题目 ID 与结果 |
| 正式查题 | `query.*`：题目、题型、解析后的选项、图片数量、本地命中或未命中、并发复用、来源回退、冲突和最终答案 |
| 正式上游请求 | `provider.*`：来源 ID、模型、接口地址、请求方法和字段名称、超时、DNS／连接／HTTP／JSON 阶段、响应字段名称、映射结果、耗时及用量 |
| 单源测试 | `provider.test.*` 和失败时的 `provider-test`：测试题目、来源、请求与网络阶段、HTTP 状态、答案、失败原因；匹配失败记录提取值与选项 |
| 答案存储 | `question.stored` / `question.store.failed`：题目指纹、数据库题目 ID、来源、答案、核验与冲突标记，或错误位置 |
| 未捕获异常 | `process.uncaught`：异常类型、错误代码、调用位置及异常来源；保留 Node 原有异常退出行为 |

成功的健康检查不重复写访问日志，静态资源访问不逐条记录；失败的健康检查仍有错误记录。来源返回未命中会记录 `miss` 或 `no_answer`，与连接失败、HTTP 错误和解析失败区分。

## 内容与脱敏

日志保留必要的题目、选项、答案和配置变更信息，方便重现格式问题。日志目录应由运维账号管理，分享前检查业务内容。

密码、Token、API Key、Authorization、Cookie、CSRF、会话、密钥、密码哈希、加密密文和模型推理字段会按字段名隐藏。已知请求或来源凭据被回显到答案文本时也会替换。URL 不记录账号、密码、查询参数或片段；不打印完整请求头和完整原始上游响应。

字符串超过 2000 字符会标记截断，数组最多记录前 20 项，对象字段和层级也有上限。日志是排查样本，不是完整数据备份。错误保留名称、代码、数据库约束及调用位置，不输出可能携带凭据或 SQL 内容的原始错误消息、数据库详情和子进程输出。

## 推荐排查顺序

1. 从页面取得请求编号，在当前和历史文件中定位 `http.request.failed` 或 `http.request.completed`。
2. 判断是鉴权、字段校验、限流还是服务端异常；内部错误结合 `error.code`、数据库约束和调用位置定位代码。
3. 查题问题找到 `queryId`，检查 `query.local`、`provider.started`、网络阶段和 `provider.mapping`。
4. HTTP 200 仅表示接口响应成功，继续检查业务状态、最终回答提取和答案匹配。
5. 答案匹配失败时，对比提取值、类型和当前选项，确认格式差异，再根据已证实的返回修改适配。
6. 修复后使用同一道题复测，确认成功记录及最终答案；真实供应商仍需在实际配置下验证。
